## CRITICAL BUG FOUND

**`server/routers.ts` line 273 — `claim.initiate` calls `assertVaultOwner(input.vaultId, ctx.user.id)`**

This is logically backwards. A vault owner cannot initiate a claim on their own vault — that's the beneficiary's action. The current code means only the owner can call this procedure, making the entire claim flow non-functional for actual beneficiaries. Must be refactored to use beneficiary-scoped authentication.

## SIDE A: VAULT OWNER FLOWS

### Account Creation (Enhanced)
- Full legal name + email + phone (all required)
- Email verification (OTP)
- Phone verification (SMS OTP)
- Password with complexity requirements (uppercase, lowercase, digit, special char, 12+ chars)
- 2FA/MFA setup (TOTP via authenticator app — required, not optional)
- Wallet connection (MetaMask, WalletConnect — required for vault creation)
- Terms of Service + Privacy Policy + Digital Asset Disclaimer acceptance (logged with timestamp + IP)

### Vault Setup (Enhanced)
- Vault name + description
- Digital asset inventory (chain, token type, contract address, estimated value)
- Document uploads: will, trust document, letter of instruction, digital asset inventory PDF
- All documents encrypted at rest (AES-256-GCM, key derived from user's wallet signature)
- Check-in interval: minimum 30 days, maximum 365 days, with recommended defaults
- Grace period: minimum 7 days, maximum 90 days
- Guardian threshold: minimum 2, maximum of (guardians - 1)
- Emergency contact (separate from guardians — notified but no claim power)
- Legacy messages: pre-written messages delivered to beneficiaries upon claim completion

### Guardian Designation (Enhanced)
Required fields:
- Full legal name
- Email address (verified via invitation)
- Phone number (verified via SMS)
- Wallet address (required — guardians MUST have wallets)
- Relationship to vault owner
- Government ID upload (encrypted, stored only as hash for ZKP verification)

Guardian Invitation Flow:
1. Owner fills in guardian details → system sends invitation email + SMS
2. Guardian clicks link → creates account (or logs in)
3. Guardian verifies identity (email OTP + SMS OTP)
4. Guardian connects wallet
5. Guardian reads and accepts "Guardian Responsibility Agreement" (legal document)
6. Guardian is marked as "confirmed" — on-chain transaction records acceptance
7. Owner receives notification of guardian acceptance

Guardian Rules:
- Minimum 3 guardians, maximum 7
- Threshold must be >= 2 and <= (guardians - 1)
- Guardian replacement: owner can replace, but change has 30-day cool-down
- If a guardian becomes unresponsive (doesn't check in annually), owner is prompted to replace
- Guardians receive annual "wellness check" email confirming they're still willing to serve

### Beneficiary Designation (Enhanced)
Required fields:
- Full legal name (must match government ID)
- Date of birth
- Email address
- Phone number
- Relationship to vault owner
- Government ID upload (encrypted)
- Identity commitment hash (generated from ID for ZKP verification)
- Allocation percentage (must total 100% across all beneficiaries)
- Wallet address (OPTIONAL at setup — can be provided during claim)

Non-Wallet Beneficiary Path:
- System stores identity commitment hash
- During claim, beneficiary is guided through wallet creation
- Custodial fallback: system creates a managed wallet, releases assets there
- Legal representative path: attorney with wallet can claim on behalf of minor/incapacitated

Beneficiary Rules:
- At least 1 beneficiary required
- Contingent/alternate beneficiaries supported (if primary can't claim within 90 days)
- Changes have 14-day cool-down period
- Beneficiary receives notification that they've been designated (but NOT vault contents)
- Minor beneficiaries: must designate a legal guardian who claims on their behalf

### Cool-Down Periods (NEW)
All critical changes are logged to `vaultChangeLog` table and have mandatory delays:
- Guardian add/remove: 30 days
- Beneficiary add/remove/change: 14 days
- Threshold change: 14 days
- Vault revocation: 7 days
- Check-in interval change: 7 days

This prevents deathbed manipulation and social engineering attacks.

### Ongoing Maintenance
- Check-in: simple "I'm alive" button + optional note
- Check-in reminders: 7 days before, 3 days before, 1 day before, day-of
- Annual vault review: system prompts owner to review guardians, beneficiaries, documents
- Vault health dashboard: shows guardian responsiveness, document freshness, last check-in
- Activity audit trail: every action logged with timestamp, IP, device fingerprint

## SIDE B: CLAIM PROCESS

### Phase 1 — Detection
1. Dead man's switch triggers (check-in interval + grace period exceeded)
2. System enters WARNING state → sends notifications to owner (email + SMS + push)
3. Grace period runs → vault enters CLAIMABLE state
4. All guardians notified: "Vault owner has not checked in. A claim may be initiated."
5. Emergency contacts notified (info only, no claim power)

### Phase 2 — Claim Initiation
1. Beneficiary logs in (or creates account) → initiates claim
2. System verifies beneficiary is designated for this vault
3. Beneficiary uploads death certificate (PDF)
4. Death certificate verification:
   - OCR extraction of key fields (name, date, certificate number)
   - Cross-reference with vault owner's name
   - Chainlink Functions oracle verifies against vital records API (when available)
   - Manual review fallback: 2 guardians must verify the death certificate
5. 72-hour cooling period begins (prevents hasty claims)

### Phase 3 — Identity Verification
1. Beneficiary completes identity verification:
   - **With wallet**: Sign SIWE message → ZKP proof against identity commitment
   - **Without wallet**: Guided wallet creation → then same flow
   - **Legal representative**: Attorney provides bar number + POA document → custodial claim
2. Government ID liveness check (selfie holding ID)
3. SMS OTP verification
4. Email OTP verification

### Phase 4 — Guardian Consensus
1. All guardians notified to vote
2. Each guardian reviews: death certificate, beneficiary identity, claim details
3. Guardians sign approval on-chain (or reject with reason)
4. Threshold met → proceed to release
5. If threshold NOT met within 30 days → dispute resolution
6. Dispute path: arbitration panel or court order upload

### Phase 5 — Asset Transfer
1. Smart contract releases assets to beneficiary wallet(s)
2. Each beneficiary receives their allocation percentage
3. Transfer receipt generated (on-chain TX hash + human-readable summary)
4. Tax documentation: estimated fair market value at time of transfer
5. IRS Form 706 guidance provided (if applicable)
6. All transfer records archived permanently

### Phase 6 — Post-Claim
1. Vault marked as CLAIMED (immutable)
2. Legacy messages delivered to beneficiaries
3. Legacy documents released (encrypted files decrypted for beneficiaries)
4. Record retention: all data preserved for 7 years minimum (tax/legal requirement)
5. Optional: memorial page with owner's legacy message

## SECURITY MODEL

- All PII encrypted at rest (AES-256-GCM)
- Government IDs stored as hashes only (full docs on encrypted IPFS/S3)
- ZKP identity proofs: prove identity without revealing documents
- All critical actions require 2FA
- Session tokens: 48hr expiry, refresh tokens, server-side revocation
- Rate limiting on all auth endpoints
- CSRF protection on state-changing operations
- Audit trail: immutable log of every action
- Data retention: 7 years post-claim (legal requirement)
- Compliance targets: SOC2 Type II, GDPR, CCPA, BIPA (biometric data)
